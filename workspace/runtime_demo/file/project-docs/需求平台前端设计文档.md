# 需求管理平台（rqrmnt-platform）前端设计文档

> 基于 `src/` 全量代码阅读整理。版本：0.0.0 · 技术栈：Vue 3 + TypeScript + Vite + Pinia + 原生 CSS。

---

## 1. 项目定位

业务需求协作平台前端，覆盖需求从「创建 → BRD 撰写 → 派发 → 承接 → PRD 拆解 → 业务审核 → 完成」的全生命周期，并以 AI Agent 会话驱动流程推进。由 6 月 24 日演示版迁移而来，已接入内网业务后端（`/apbm`）与中心化 Harness 网关（`/api/harness`）。

### 1.1 核心用户角色

- **业务经理**（如王大陆）：发起需求、撰写 BRD、提交审核、通过/退回 PRD
- **产品经理**（如李一飞等）：承接任务、编写 PRD、提交业务审核
- **AI Agent 团队**：群聊负责人 / 需求澄清助手 / BRD 草拟助手 / 派发建议助手（见 `constants/index.ts:AGENT_STEPS`）

### 1.2 功能模块总览

| 页面 | Hash 路由 | 说明 |
|------|----------|------|
| 首页 | `/#/home` | 快速创建需求、待办/最近事项列表、空间筛选 |
| 工作台（泳道看板） | `/#/pool` | 按「业务需求 / 需求待承接 / 产品拆解 / 业务审核中 / 已完成」五泳道展示卡片 |
| 会话工作区 | `/#/workspace` | 左侧会话树 + 中部聊天面板 + 右侧协作文档面板 |
| 资产检索 | `/#/asset-search` | 关键词分页搜索业务资产 |
| 资产矩阵 | `/#/asset-matrix` | 价值链 → 领域 → 系统 → 功能四级下钻 |
| 资产详情 | `/#/asset-detail` | 详细信息 / 标签 / 血缘 Tab |
| 领域主题明细 | `/#/asset-domain-detail` | 矩阵下钻后的功能列表 |
| 应用拆解 | `/#/app-decompose` | 已审批待拆解任务的节点编辑 |
| 登录 | `/#/login` | 用户名密码登录 |
| 天弓登录 | `/#/tglogin?token=…` | SSO Token 登录（兼容旧路径 `/tglogin`） |

## 3. 路由与导航设计

### 3.1 路由表（`router/index.ts`）

```
/login                    → LoginPage（懒加载）
/tglogin                  → SsoLogin（懒加载）
/                         → AppShell（布局壳）
  /home                   → HomePage
  /pool                   → PoolPage
  /workspace              → WorkspacePage
  /asset-search           → AssetSearchPage
  /asset-matrix           → AssetSearchPage（同一组件，Tab 不同）
  /asset-detail           → AssetDetailPage
  /asset-domain-detail    → AssetDomainDetailPage
  /app-decompose          → AppDecomposePage
/:pathMatch(.*)*          → redirect /home
```

所有页面均使用 `() => import(...)` 懒加载。

### 3.2 导航守卫（`connectAppRouter`）

1. **认证守卫**：未登录访问非 login/tglogin 页面 → 强制跳转 `/login`
2. **资源存在性守卫**：`asset-detail` 需 `store.activeAssetItem`、`asset-domain-detail` 需 `store.activeDomainDetail`，否则回退 `asset-search`
3. **工作区进入准备**：首次进入 `workspace` 时先设 `conversationEntering=true` + 切壳层，再 `await ensureWorkspaceSessionList({refresh:true})` 加载会话列表
4. **afterEach 同步**：`store.page = to.name`（唯一 route→store 写入点）；`asset-search/matrix` 同步 `assetViewTab`；外部进入 `pool` 时 `enterWorkbench()`；进入 `home` 且已登录时 `restoreAuthRecovery()`
5. **登出监听**：`watch(store.isAuthenticated)` → 未登录且不在 tglogin → `replace('/login')`

### 3.3 Store ↔ Router 解耦

`navigation.ts` 提供 `bindPageNavigation` / `navigateToPage`，store 中 `setPage()` 通过 WeakMap 查找当前绑定的 navigate 函数，避免循环依赖。

### 4.2 会话同步 Store（`stores/conversationSync.ts`）

独立 Pinia store，维护 Harness 会话的**不可变事件归约状态**：

- 数据源：SSE 事件流（`eventStream.ts`）+ REST 快照（history、status、children、todo、questions、permissions、dispatch suggestion、system selection、task acceptance cards）
- 状态：`message` / `part` / `toolCard` / `task` / `question` / `permission` / `harnessSession` / `harnessChildren` / `sessionTodo` / `businessError`
- 优化：`optimistic.message/part`（发送中的乐观消息，2min 确认窗口）、消息内容缓存（WeakMap by revision）、工具卡折叠（同 requirementId+brdSessionId 只保留最新 dispatch-suggestion / system-selection）
- 显示：`displayMessagesForScope(scopeId, userName, leaderId)` 将多 session 事件合并为单一时间线

### 4.3 其他 Store

- `delivery.ts`：BRD 审核清单（`fetchDelivery` / `deliveryReview`），含版本比对
- `attachmentDraft.ts`：附件草稿（按 userId+sessionId 隔离），支持上传队列、解析、重试

## 5. 实时通信设计（SSE）

### 5.1 事件流（`services/eventStream.ts`）

- 协议：HTTP POST → SSE 流（Harness 网关）
- 心跳：服务端每 10s 发 ping；客户端 35s 无数据视为 stale → 主动断开重连并补拉历史
- 重连：指数退避 250ms → 10s，健康后重置；403/404 连续 3 次放弃（鉴权类错误不重试）
- 事件归一化：`harnessEventAdapter.normalizeHarnessEvent(raw) → ConversationEvent`
- 批量刷新：`FLUSH_FRAME_MS = 16ms`（requestAnimationFrame 对齐）
- 鉴权：每个 session 独立 `X-User-Token` + `directory`，存于内存 Map（`harnessSessionUserTokens` / `harnessSessionDirectories`）

### 5.2 事件类型（`types/conversation.ts`）

```
message.updated / message.part.updated / message.part.delta
tool.card.updated / tool.card.removed
task.updated
question.updated / question.answered
permission.requested / permission.responded
business.error
session.status.updated
schedule.updated
```

### 5.3 会话恢复流程（`restoreHarnessSession`）

进入会话时并发拉取 9 组数据（`Promise.allSettled`）：

1. `fetchConversationHistory(sessionId, {limit:50})` — 消息历史
2. `fetchSessionStatus(signal, sessionId)` — 各 session 状态
3. `fetchHarnessSession(sessionId, signal)` — 会话元信息
4. `fetchHarnessSessionChildren(sessionId, signal)` — 子会话树（BFS，每层最多 3 并发，带版本缓存）
5. `fetchPendingQuestions(signal, sessionId)` — 待回答问题
6. `fetchPendingPermissions(signal, sessionId)` — 待授权请求（自动允许白名单外的）
7. `fetchRequirementDispatchSuggestion(sessionId, signal)` — 派发建议卡
8. `fetchRequirementSystemSelection(sessionId, signal)` — 系统选择卡
9. `fetchRequirementTaskAcceptanceCards(sessionId, signal)` — 任务承接卡

附加：`refreshHarnessSchedule` + `fetchHarnessSessionTodo`（optional，不阻塞主流程）

全部 fulfilled → `complete=true`；任一 rejected → `conversationSyncError` 提示用户。

## 6. 业务工作流设计

### 6.1 需求生命周期

```
[首页/项目] 创建需求
     │
     ▼
业务需求会话（BRD 撰写中）
  ├── AI Agent 协助：需求澄清 → BRD 草拟
  ├── 业务经理编辑 BRD（Tiptap 协同编辑器，Yjs 实时同步）
  └── BRD 前四章确认后 → 触发派发
     │
     ▼
派发阶段
  ├── AI 生成派发建议卡（dispatch-suggestion card）
  │   ├── 系统选择卡（system-selection card）：为每个任务选承接系统
  │   └── 确认负责人（mention 候选人列表）
  ├── 业务经理在卡上确认 → uploadRequirementCurrentBrd → sendConfirmationMessage
  └── 取消派发 → cancelRequirementDispatchSuggestion
     │
     ▼
需求待承接（任务分发给产品经理）
  ├── 产品经理收到 task-acceptance card
  ├── 操作：承接 / 拒绝（填原因）/ 转派（选新人）/ 撤回
  └── 承接成功 → 自动进入 PRD 会话（openAcceptedPrdSession，轮询 3 次等 prdSessionId 出现）
     │
     ▼
产品拆解（PRD 撰写中）
  ├── AI Agent 协助：产品定义 → 业务流程 → 功能矩阵 → 功能细节 → 质量审查
  ├── 产品经理编辑 PRD（Tiptap 协同编辑器）
  └── PRD 退回修改 → 继续修改（continueProductRevision）
     │
     ▼
业务审核中
  ├── 产品经理提交审核（SUBMIT_REVIEW）
  ├── 业务经理审核：通过（REVIEW_APPROVE）/ 退回（REVIEW_REJECT + 原因）
  └── 审核通过 → 已完成
     │
     ▼
已完成
  └── 可选：启动技术功能点拆解（startTechnicalBreakdown）
```

### 6.2 泳道映射（`_mapTaskStatusToLane`）

| 任务状态（中文） | 泳道 |
|---|---|
| 撰写中 / 已承接 | 业务需求 |
| 待承接 | 需求待承接 |
| 拆解中 / 退回修改 | 产品拆解 |
| 待业务审核 | 业务审核中 |
| 已完成 | 已完成 |

### 6.3 权限模型

- **stake 判定**（`conversationStakeForUser`）：根据需求 creator / part.owner 判断当前用户是 `business` 还是 `product`
- **allowedActions**：由 Harness schedule 下发（`sync.task[taskId].allowedActions`），前端 `canRunAction(action, {allowedActions, fallback})` 双重校验
- **readonly 标志**：会话级 `conversation.readonly`，已完成泳道进入时锁定输入
- **发起人保护**：`ownsRequirementFromState` 基于 `creatorUserId` 精确匹配（非姓名回退）

### 6.4 空间（工作空间）设计

- 空间 = 业务域隔离单位，对应后端 `workspaceId`
- 默认空间（`isDefault` 或名称「默认空间」）不可删除/重命名
- 需求归属空间：`spaceAssignments[requirementId] → spaceId`，持久化到 localStorage + 后端 `transferRequirement`
- 侧栏按空间分组展示会话树；首页/工作台支持空间筛选

## 8. 认证与安全设计

### 8.1 登录方式

1. **账号密码**（`/login`）：`POST /apbm/auth/login` → 返回 userId、ssoNo、realname、token
2. **SSO Token**（`/tglogin?token=…`）：天弓客户端传递 URL 编码 token
3. **旧路径兼容**：`/tglogin`、`/tglogin/`、`/tglogin/index.html` → Nginx rewrite → `index.html` → 前端 `legacyTgloginUrl` 转为 `#/tglogin?token=…`

### 8.2 Token 管理

- 业务后端：`X-RMPF-Access-Token` + `X-RMPF-SSO-No` 请求头，localStorage 持久化
- Harness：每会话独立 JWT（`harnessUserToken`），内存 Map 按 sessionId 隔离；过期时 `refreshHarnessUserToken` 续期
- 身份隔离：JWT claims（iss+sub）解码为 subject，不同用户 token 不会串用

### 8.3 过期恢复（authRecovery）

- `verifyBusinessSession` 定期校验；过期 → `beginReauthentication`
- 保存恢复上下文（userId、ssoNo、sessionId、cardKey、draft、attachments）到 sessionStorage
- 重新登录后 `restoreAuthRecovery` 恢复原会话 + 草稿
- Electron 客户端通知：`electronAPI.sendMessage('login'/'logout', …)`

### 8.4 安全约束

- 敏感凭证（token）不写入 console（仅 fingerprint + length）
- XSS 防护：markdown 渲染经 `dompurify` 清洗
- 权限操作前后双重校验（前端 allowedActions + 后端接口鉴权）

## 9. 数据流设计

### 9.1 典型数据流：创建需求 → 进入会话

```
用户输入 prompt + 附件
  → HomePage.createDemand()
  → store.createBusinessDemand({projectId, initialPrompt, attachments})
  → [后端模式] addRequirement(workspaceId, title) → {requirementId, sessionId, harnessUserToken, harnessDirectory}
  → rememberHarnessSessionDirectory/UserToken
  → configureHarnessConnection（激活会话）
  → [有附件] attachmentDraft.addFiles → waitForParsed
  → finishLocalCreate（upsertRequirement + upsertConversation）
  → openConversation(cardKey)
  → setPage('workspace') → router.push('/workspace')
  → restoreHarnessSession（并发拉取 9 组数据）
  → conversationEventStream.start(sessionId)（SSE 建立）
  → [无附件且有文字] sendConversationMessage（首条消息）
```

### 9.2 典型数据流：派发确认

```
用户在 dispatch-suggestion 卡上选择负责人
  → store.confirmDispatchSuggestion(card, selections)
  → 校验：requirementId 真实、card 版本一致、领域/系统/负责人完整
  → uploadRequirementCurrentBrd(sessionId, {cardId, expectedCardUpdatedAt})

  → sendConversationMessage（system-notice）
  → trackRequirementDispatch（SSE 监听 tool card 状态变化）
  → 结果处理：succeeded / failed / invalidated / superseded
  → loadProjects + invalidateWorkspaceSessionList
```

### 9.3 典型数据流：PRD 审核

```
产品经理点击「提交审核」
  → store.submitReview()
  → runAiReviewAction(taskId, {action:'SUBMIT_REVIEW'})
  → [delivery.supported] fetchDelivery → deliveryReview(sessionId, action, reason, version)
  → [else] buildPrdReviewConfirmationMessage → sendConversationMessage
  →    waitForRequirementReviewResult（SSE 监听特定 tool part completed/error，2min 超时）
  → 更新本地 part.status / lane / workflowTask.status
  → sync.setSendError(null)
```

## 10. 性能与体验设计

### 10.1 虚拟滚动

- `VirtualTimeline.vue`：长会话消息虚拟列表，避免 DOM 爆炸

### 10.2 请求合并与缓存

- `workspaceListRequests`（WeakMap）：相同 user+version 的并发请求去重
- `scheduleRefreshInFlight`（WeakMap）：同一 session 的 schedule 刷新去重
- `childHistoryVersions`（WeakMap）：子会话历史 30s 内复用（非 busy 状态）
- `messageContentCache` / `messageDisplayCache`（WeakMap）：消息渲染缓存（by revision）

### 10.3 懒加载

- 所有路由组件 `() => import(...)`
- 动态 `import()` 延迟加载大模块（如 `fetchRequirementLogs`、`fetchRequirementProgressList`、`fetchTodoQuery`）
- `optimizeDeps.include: ['marked', 'dompurify']`

### 10.4 视口适配

- `useViewportScale`：CSS zoom 缩放（适配大屏/小屏）
- `fitViewport`：初始视口计算
- `workspaceViewport` 三档响应式布局

### 10.5 骨架与过渡

- 进入会话：spinner 遮罩 + 文案（「正在进入会话中...」「正在进入PRD会话中...」）
- 后端加载中：`backendFallbackNotice` 顶部提示
- 静默刷新：30s 内进入 workspace 不重复拉取会话列表

## 15. 已知限制与技术债

1. **主 store 过大**（6354 行）：所有业务逻辑集中一处，后续可按领域拆分
2. **部分 API 已下线**：`fetchDocument` / `saveDocument` / `fetchRequirementProgress` 等标记为跳过，文档读写完全依赖 Yjs 协同
3. **演示种子数据**：`data/mock.ts` 仍被引用（无 API 时的 fallback），后端模式下不使用
4. **console.info 调试日志**：大量 `[HarnessSessionTrace]` / `[TaskAcceptanceNavigation]` 前缀日志，生产环境应移除
5. **无 UI 组件库**：全部手写 CSS + 自定义组件，一致性靠约定维护
6. **localStorage 持久化**：spaces / spaceAssignments / auth 存 localStorage，跨设备不同步
7. **部分输入框缺少 maxlength**：拒绝原因、退回原因、重新拆解原因、AI 修改指令等 textarea 未设显式长度上限，仅靠 trim 非空校验，建议补充统一上限
