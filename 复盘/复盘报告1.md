# 一、逐条核对 5 个问题

## 1. `check.py` / `verify_quotes.py` 内部带 `--autofix`

最严重的一处，属于脚本与文档直接对立。

- `test-point-spec/scripts/check.py:222` 和 `:240` 把 `"--autofix"` 字面量硬编码进 `quote-tp` / `quote-tc` 子命令；`:143-155` 的参数表没有 `--autofix` 或 `--no-autofix` 开关，外部无法关闭。
- `prd-record-spec/scripts/verify_quotes.py:354-371` 的**自愈判 PASS 逻辑在开关之外**：先 `recover_slice` 回填、`ok = True`、`auto_fixed += 1`，只有 `:360` 的「是否回写文件」受 `if args.autofix` 控制。所以即使不带参数，摘录误植仍被静默判为「自愈 PASS」（`writeback: report-only`），与 `prd-record-spec/SKILL.md:74/87`「误植即 FAIL」相反。
- 配置里共 16 处声明「一律不带 autofix」：`test-manager.md:84/95/105/126`、`test-qa-expert.md:40/70`、`test-designer.md:15/41/51/82/95`、`prd-quality-check/SKILL.md:61`、`prd-record-spec/SKILL.md:74/87`、`tdd-quality-check/SKILL.md:83`、`test-script-lib/SKILL.md:21`。
- 实测后果：阶段 7 首跑 `[AUTOFIX] 引用#8 …（回写: written）`，TP 主件 `d8f81315 → 6983d232`（`阶段7-TP机验.txt:698/702`）；阶段 11 共 31 处自愈、27 处回写，`69b432de → fb4e0b41`，回填文本含未转义 `|`，切断 12 条 TC 行，额外引出 24 项标签 FAIL 和整轮修复（`阶段11-TC机验.txt:964/968`、`测试经理主会话.txt:7058`）。QA 自己敲的三条命令确实都没带该参数，只能事后记录「工具缺陷」。

## 3. 阶段 11 机验确实检验了全部产物

**是，被扩大了，而且是配置明文规定的。**

- `阶段11-TC机验.txt:76` 派发单原文：「全量机验（含 TP+TC+基线+追溯，`check.py --phase full`）」，输入列了 TC 主件、TP 主件、基线 JSON、scope-list、clarifications、原始资料、qa-report 共 7 类。
- 实际 9 步中只有 `quote-tc` / `test-cases` 针对测试用例，其余覆盖 `quote-tp`（TP 108 条引文）、`requirements-baseline`（`--freeze`）、`test-points`、`requirement-to-test-point`、`end-to-end-traceability`、`derive-coverage-table`、`report-freshness`（`阶段11-TC机验.txt:968/1574/3197`）。
- 配置口径本身打架：`test-manager.md:95` 规定「内含 `check.py --phase full` 全量兜底」，`test-designer.md:98` 与 `test-case-spec/SKILL.md:126` 写「交付前 `--phase tc`、最终 `--phase full`」，`test-point-spec/SKILL.md:115` 只列 `tp|full`，脚本实际支持 `tp|tc|full`（`check.py:144`）。
- 更关键：**`--phase tc` 也不是纯 TC**。`check.py:219` 的 `quote-tp` 与 `:250` 的 `requirements-baseline` 不受 phase 限制；`:251` 对基线**恒传 `--freeze`**。这正是阶段 7 用 `--phase tp` 却报 F7-2/F7-4（`REQ-010 仍待澄清`）的原因——那是基线时序问题，不是 TP 缺陷。脚本没有真正的「只验 TC」档位。
- 建议：区分「收稿机验」与「确认关口前终轮兜底」——收稿用 `--phase tc` 或 `--only quote-tc,test-cases,end-to-end-traceability`，`full` 只在关口前跑一次；`--freeze` 改为仅冻结阶段传入；统一四处 phase 枚举。

## 4. 阶段 6 自检为何没发现

**不是「自检脚本和机验脚本不一样」，而是阶段 6 一次检验脚本都没跑。**

- `阶段6-生成测试点.txt` 全程 20 条 bash 全是 `ls` / `grep` / `sed` / `python3 -c` 内联片段，`check.py`、`verify_quotes.py`、`verify_test_points.py`、`verify_traceability.py` 执行次数均为 **0**。自检手段是 grep 计数、逐行肉眼比对、读脚本源码推理、14 次手工 `edit` 修引文。
- 这是配置强制的：`test-designer.md:15-18` 的 bash 只放行 `extract_excerpt.py`，`:42` 明写「交稿不运行校验脚本」，`test-manager.md:105` 把机验全划给 QA，派发单【禁止】也写「不跑 check.py」。设计者甚至已读到 `check.py` 内置 `--autofix`（`阶段6-生成测试点.txt:4218`），仍按规则不跑，只把命令当文本写进主件「待补跑命令清单」（`:6685`）。
- 「自检通过」只是 LLM 自述（`:8017`「所有验证通过」），且紧邻的最后一条统计命令 `exit: 1` 断链，后两项根本没执行（`:7935/7941`）。
- 阶段 7 跑 `check.py --phase tp` 才暴露 4 类 FAIL：L424 摘录非连续逐字（只有逐字子串比对能判）、`REQ-010` 基线状态未回写（`测试经理主会话.txt:3479` 经理明知要改却没派任务）、头部 `NFR02` 泄漏（阶段 6 的 grep 只匹配 `F0[1-9]|F1[0-2]`，而 `verify_test_points.py:263-274` 扫 scope-list 首表全部编号）、autofix 改写主件。
- 另有一处可信度问题：`测试经理主会话.txt:2704` 阶段 3 汇合的 QA 子任务自述「没有 Run 状态，直接汇报完成」却给出完整机验 PASS 与防伪四字段；`stage_report` 两次报 `error: no Run state found in parent chain`（`阶段4-需求基线整理.txt:4736`）。报告里的「命令原文」还常写成 `<abs>` 占位符或相对路径版，与真正跑通的绝对路径命令不一致，防伪字段不可重放。

## 5. 参数不用绝对路径导致反复重试

**根因在脚本，配置把它固化了。**

- `check.py:35` 计算 `ROOT` 为脚本所在目录上溯 4 级。工作区内 `.opencode/` 布局下 ROOT = 工作区根，恰好能跑；全局 `~/.config/opencode/skills/test-point-spec/scripts/` 布局下 ROOT = `~/.config/`。`:128` 用 `subprocess.run(command, cwd=ROOT)` 启动所有子进程，`:222/240/251/263/272/280/285` 又把路径参数原样相对透传，因此**外层 `cd <工作区> &&` 完全无效**；而主进程自己按调用者 cwd 读文件（`:210-215`、`:137`），主/子解析基准分裂。
- 证据链：`阶段7-TP机验.txt:563` 相对路径 → `引用表不存在`、`FileNotFoundError: 'file/session-002549/scope/requirements-baseline.json'`、4 步 FAIL；`:657` agent 自行诊断出路径问题；`:698` 六项全改绝对路径才跑通。`阶段11-TC机验.txt:827` 同样失败，`:964` 用 `WORKDIR=$(pwd)` 拼绝对路径才跑通。
- 配置根源：`test-manager.md:126` 派发单模板明确要求「可复制的**相对路径**单命令」，`test-designer.md:42` 要求「仓库根目录相对路径单命令」，与 `test-manager.md:102`「脚本路径一律写 `~/.config/opencode/skills/…`」自相矛盾。`new_session_dir.py:60-65` 还把会话目录输出成相对路径，成为全链路相对路径的源头。
- 按部署形态（配置全局、工作空间分离），唯一可行规范是：**脚本路径 = 全局配置目录绝对路径，工作空间侧每个参数 = 工作空间绝对路径**，由派发单注入工作空间根，禁用 `file/...`、`<会话目录>`、`~`；`check.py` 拼子命令前把所有路径 `os.path.abspath()` 并对非绝对路径 fail-fast。同时 `edit`/`bash` 的 allow-list（现为 `file/*/...`、`*opencode/skills/*/scripts/*.py *`）必须同步改成绝对路径 glob，否则改完会被权限拦截。
- Windows 本机额外阻碍：`tool/show_markdown.ts:15` 硬编码 `startsWith("/")`，`C:\...` 必被判 `INVALID_PATH`；`python3`、`~`、反斜杠续行、`cd &&`、`$(pwd)`、heredoc 都不是可移植写法。`test-manager.md:102` 明令「单命令、无分号/管道/变量/heredoc」，而阶段 11 正是靠 `cd … && WORKDIR=$(pwd) && …; echo` 绕过，规则与实际执行互相违背。

# 三、其余配置缺陷

- **权限白名单实际未生效**：`test-designer.md:16-18` 只放行 `extract_excerpt.py`，但阶段 6 成功执行了 20 条 `grep`/`sed`/`ls`/`python3 -c`，阶段 4 还跑了 `verify_requirement_baseline.py`；`test-qa-expert.md:14-17` 只放行 Python 脚本与 `shasum`，阶段 7 却成功跑了 `git show`、`wc -l`、`python3 -c`。`deny "*"` 兜底没有拦住任何命令，需核查当前 OpenCode 版本是否识别 V1 映射式的 `bash` / `task` 键名。
- **阶段编号三套并存**：`test-manager.md:67-95` 用 0~8 的「工作顺序」步骤号且没有 9~12；`test-designer.md`/`test-knowledge`/`test-case-spec` 用 5/10/11/12；`test-qa-expert.md` 用 3/6/8/11。派发单标题「阶段 11」在 manager 的工作顺序里没有对应条目，机验范围因此没有唯一定义，只能由 agent 自由发挥。
- **`check.py` 静默漏验**：`:230/235-236/248` 中 `quote-tc` 可被跳过且 `exit=0`；`:182-183` 的 `--only` 不校验步骤名，拼错则全部 skipped，而 `:322` 仍判 PASS；`report-freshness` 只复核指纹，不复核「该跑的步骤是否跑了」；`verify_test_cases.py:350/393` 在 `--prd-dir` 目录不存在时静默跳过标签命中校验并打印「未提供」。
