# `.opencode` 团队生成测试用例问题汇总复盘

## 1. 复盘范围与结论

本文合并 `复盘报告1.md` 与 `复盘报告2.md` 两次独立复盘的结论与证据，按主题去重，并补入本次对配置文件的复核结果。两次复盘结论一致、证据互补。

排查材料：6 份对话记录（`测试经理主会话.txt` 约 8520 行、`阶段4-需求基线整理.txt`、`阶段6-生成测试点.txt`、`阶段7-TP机验.txt`、`阶段11-TC机验.txt`、`阶段11-TC修复.txt`）、3 个 agent 配置、8 份 `SKILL.md`、13 个脚本、`tool/show_markdown.ts`、`opencode.jsonc`、`.selftest.sh`、`.setup_demo.sh`。对话实际跑在 Linux harness 环境（`/home/harness/.config/opencode/skills/` + 独立工作空间），本机为 Windows，两者都属「配置全局、工作空间分离」的部署形态。

一句话总因：`check.py` 有三个与文档相反的硬编码（强制 `--autofix`、子进程 `cwd=ROOT`、基线恒传 `--freeze`），叠加多份 `SKILL.md` 路径引用落空、命令模板清一色相对路径、生成者被禁止跑校验脚本、agent 编排口径分裂，使阶段 7/11 的失败、回写与重试全部可复现。这不是执行偶发失误，而是配置与脚本实现互相矛盾的必然结果。

| 根因层级 | 表现 | 代表位置 |
|---|---|---|
| 脚本内部硬编码 | 强制自愈回写、子进程工作目录改到配置目录、基线无条件冻结 | `check.py:35/128/222/240/251`、`verify_quotes.py:354-371` |
| 资源路径口径 | 跨 skill 裸名、不存在的 `tests/`、脚本接口不兼容 | 8 份 `SKILL.md` |
| 编排口径分裂 | 阶段编号三套、phase 枚举三套、机验归 QA、生成者禁跑校验 | 3 个 agent 与 `test-case-spec/SKILL.md` |
| 路径规范与部署形态 | 相对路径与占位符模板，不适配全局配置加分离工作空间 | `test-manager.md:102/126`、`new_session_dir.py:60-65` |

## 2. 五个核心问题

### 2.1 `--autofix`：命令不带，脚本内部强制开

- `check.py:222` 与 `:240` 把 `"--autofix"` 字面量拼进 `quote-tp` / `quote-tc` 子命令，`:143-155` 的参数表既无该开关也无 `--no-autofix`，外部无法关闭。配置里共 16 处声明「一律不带 autofix」：`test-manager.md:84/95/105/126`、`test-qa-expert.md:40/70`、`test-designer.md:15/41/51/82/95`、`prd-quality-check/SKILL.md:61`、`prd-record-spec/SKILL.md:74/87`、`tdd-quality-check/SKILL.md:83`、`test-script-lib/SKILL.md:21`。
- `verify_quotes.py:263` 的参数本身默认关闭（`store_true`），但 `:354-371` 的自愈判 PASS 逻辑在开关之外：先 `recover_slice` 回填、置 `ok = True`、`auto_fixed += 1`，只有 `:360-361` 的「是否回写文件」受 `if args.autofix` 控制。因此不带参数时摘录误植仍被静默判为「自愈 PASS（report-only）」，与 `prd-record-spec/SKILL.md:74/87`「误植即 FAIL」相反。独立运行该脚本得到的报告 `autofix:false / artifact_changed:false / auto_fixed:4` 是直接证据。
- 回写对象是产物主件（`check.py:218` 的 `tp_quote_src`、`args.tc_file`），`verify_quotes.py:311-314` 直接 `content.replace(old, fixed)`，不做 Markdown 转义；`check.py` 用 `capture_output=True` 吞掉输出，`run():126-139` 与 `revalidate_report():48-73` 从不解析 quote 子报告，也不读 `artifact_changed` 据此判 FAIL。
- 阶段 11 派发单甚至写「如内部强制带 autofix，记录缺陷但不影响验收」，等于把工具缺陷写进流程。QA 自己敲的三条命令确实都没带该参数，只能事后记录「工具缺陷」。

### 2.3 阶段 11 机验范围被扩大

- 派发单原文「全量机验（含 TP+TC+基线+追溯，`check.py --phase full`）」，输入列了 TC 主件、TP 主件、基线 JSON、scope-list、clarifications、原始资料、qa-report 共 7 类（`阶段11-TC机验.txt:76`）。实际 9 步中只有 `quote-tc` / `test-cases` 针对测试用例，其余覆盖 `quote-tp`（TP 108 条引文）、`requirements-baseline`（`--freeze`）、`test-points`、`requirement-to-test-point`、`end-to-end-traceability`、`derive-coverage-table`、`report-freshness`（`:968/1574/3197`）。
- 配置口径本身打架：`test-manager.md:95` 规定「内含 `check.py --phase full` 全量兜底」，`test-designer.md:98` 与 `test-case-spec/SKILL.md:126` 写「交付前 `--phase tc`、最终 `--phase full`」，`test-point-spec/SKILL.md:115` 只列 `tp|full`，`test-qa-expert.md:66` 的语义关又只查 TC；脚本实际支持 `tp|tc|full`（`check.py:144`）。
- 更关键的是 `--phase tc` 也不是纯 TC：`check.py:219` 的 `quote-tp` 与 `:250` 的 `requirements-baseline` 不受 phase 限制，`:251` 对基线恒传 `--freeze`。按 `test-manager.md:84`，基线要到 TP 确认关口才联签冻结，阶段 7 收稿时 `REQ-010` 仍是 `needs_clarification`（`测试经理主会话.txt:3479` 经理已知需改却未派任务），于是 `F7-2`（`--freeze` FAIL）与 `F7-4`（`verify_traceability.py:69-70` FAIL）必然出现——那是基线时序问题，不是 TP 缺陷。脚本没有真正的「只验 TC」档位。

### 2.4 阶段 6 自检未跑任何校验脚本

- 不是「自检脚本和机验脚本判据不一样」，而是阶段 6 一次检验脚本都没跑：全程 20 条 bash 全是 `ls` / `grep` / `sed` / `python3 -c` 内联片段，`check.py`、`verify_quotes.py`、`verify_test_points.py`、`verify_traceability.py` 执行次数均为 0。自检手段是 grep 计数、逐行肉眼比对、读脚本源码推理、14 次手工 `edit` 修引文。
- 这是配置强制的：`test-designer.md:15-18` 的 bash 只放行 `extract_excerpt.py`，`:42` 明写「交稿不运行校验脚本」，`test-manager.md:105` 把机验全划给 QA，派发单【禁止】也写「不跑 check.py」。设计者甚至已读到 `check.py` 内置 `--autofix`（`阶段6-生成测试点.txt:4218`），仍按规则不跑，只把命令当文本写进主件「待补跑命令清单」（`:6685`）。
- 「自检通过」只是 LLM 自述（`:8017`「所有验证通过」），且紧邻的最后一条统计命令 `exit: 1` 断链，后两项根本没执行（`:7935/7941`）。
- 阶段 7 跑 `check.py --phase tp` 才暴露 4 类 FAIL：`F7-1` TP-013 摘录跳过插入语「（同一需求下从 1 开始递增）」，只有逐字子串比对能判；`F7-2/F7-4` 基线 `REQ-010` 未由 `CL-002` 回写 `status`；`F7-3` TP 主件头部 `NFR02` 泄漏，自检 grep 只匹配 `F0[1-9]|F1[0-2]`，而 `verify_test_points.py:263-274` 扫 `scope-list` 首表全部编号（含 NFR）。语义关 7 项全 PASS，正好说明机器关与语义关口径不同。

### 2.5 相对路径导致反复重试

- 根因在脚本：`check.py:35` 把 `ROOT` 算成脚本目录上溯 4 级，工作区 `.opencode/` 布局下 ROOT = 工作区根，全局 `~/.config/opencode/skills/...` 布局下 ROOT = `~/.config/`；`:128` 用 `subprocess.run(command, cwd=ROOT)` 启动所有子进程，`:222/240/251/263/272/280/285` 又把路径参数原样相对透传，因此外层 `cd <工作区> &&` 完全无效；主进程自己按调用者 cwd 读文件（`:210-215`、`:137`），主/子解析基准分裂，且 `_text_of()` 遇 OSError 返回空串，把「文件不存在」伪装成「清单无直引引用」。
- 证据链：阶段 7 相对路径 → `引用表不存在`、`FileNotFoundError: 'file/session-002549/scope/requirements-baseline.json'`、4 步 FAIL（`阶段7-TP机验.txt:563`）；`:657` agent 自行诊断出路径问题；`:698` 六项全改绝对路径才跑通。阶段 11 `[6]` 相对路径轮 7 步全 FAIL、只有 `derive-coverage-table` PASS，`:827` 再次失败，`:964` 用 `WORKDIR=$(pwd)` 拼绝对路径才跑通。
- 配置根源：所有命令模板的参数都是相对路径或占位符（`test-manager.md:62-63,69,72-73,90-92,130`、`test-designer.md:64,86-88,99-101`）；`test-manager.md:126` 派发单模板明确要求「可复制的**相对路径**单命令」，`test-designer.md:42` 要求「仓库根目录相对路径单命令」，与 `test-manager.md:102`「脚本路径一律写 `~/.config/opencode/skills/…`」自相矛盾。`new_session_dir.py:60-65` 还把会话目录输出成相对路径，成为全链路相对路径的源头。
- 连带影响：路径绝对化后，`edit` allow-list（现为 `file/*/state/…`）与 `bash` allow-list（现为 `python3 *opencode/skills/*/scripts/*.py *`）必须同步调整，否则写入和命令会被权限拦截。

## 4. 其他配置缺陷

### 4.1 编排与权限

- **阶段编号三套并存**：`test-manager.md:67-95` 用 0~8 的「工作顺序」步骤号且没有 9~12；`test-designer.md` / `test-knowledge` / `test-case-spec` 用 5/10/11/12；`test-qa-expert.md` 用 3/6/8/11。同一文档内步骤号与全局阶段号也混用，派发单标题「阶段 11」在 manager 的工作顺序里没有对应条目，机验范围因此没有唯一定义，只能由 agent 自由发挥。
- **权限白名单实际未生效**：`test-designer.md:16-18` 只放行 `extract_excerpt.py`，但阶段 6 成功执行了 20 条 `grep` / `sed` / `ls` / `python3 -c`，阶段 4 还跑了 `verify_requirement_baseline.py`；`test-qa-expert.md:14-17` 只放行 Python 脚本与 `shasum`，阶段 7 却成功跑了 `git show`、`wc -l`、`python3 -c`。`deny "*"` 兜底没有拦住任何命令，需核查当前 OpenCode 版本是否识别 V1 映射式的 `bash` / `task` 键名。
- **命令形态冲突**：`test-manager.md:102` 明令「单命令、无分号/管道/变量/heredoc」，`test-qa-expert.md:16` 同样禁复合命令，但阶段 7/11 实际靠 `cd … && WORKDIR=$(pwd) && …; echo` 执行，规则与实际执行互相违背。

### 4.2 静默漏验与报告可信度

- `check.py:230/235-236/248`：给了 `--quote-table` 就整段跳过 `quote-tc`，主件无 `文件:L…「…」` 语法也直接 skipped（exit 0），与 docstring「TC 清单直引逐字机验」矛盾；`:182-183` 的 `--only` 不校验步骤名，拼错则全部 skipped 而 `:322` 仍判 PASS；`derive-coverage-table` 被排除时不留 skipped 记录；`report-freshness` 只复核指纹，不复核「该跑的步骤是否跑了」。
- `verify_test_cases.py:350/393`：`--prd-dir` 任一目录不存在时，整段标签取值命中校验（6b）静默跳过并打印「未提供 --prd-dir」，在路径分离布局下极易掩盖真实故障。
- 报告可信度：`测试经理主会话.txt:2704` 阶段 3 汇合的 QA 子任务自述「没有 Run 状态，直接汇报完成」却给出完整机验 PASS 与防伪四字段；`stage_report` 两次报 `error: no Run state found in parent chain`（`阶段4-需求基线整理.txt:4736`）。报告里的「命令原文」还常写成 `<abs>` 占位符或相对路径版，与真正跑通的绝对路径命令不一致，防伪字段不可重放。

### 4.3 文档与注释口径

- 注释层也在强化错误口径：`verify_quotes.py:8-11`、`mdtable.py:11/35`、`verify_test_points.py:52` 都把 autofix 自愈写成默认机制，与所有 `SKILL.md` 的「流程禁用」相反。
- 文档清单失真：`test-knowledge/SKILL.md:3` 写「四份原文 + 两份补充件」，实际是 3 份；`test-script-lib/SKILL.md:10-37` 模块清单漏了 `screen_intent_words.py`；phase 枚举 `tp|full` 与 `tc|full` 各漏一值；`check.py:6-16` 头注释列 8 个步骤，实际还有 `derive-coverage-table`。
- 自测脚本失效：`.selftest.sh` 只 grep 键名存在性，从不校验三个 agent `:5-6` 都警告过的「`"*": deny` 必须排在 allow 之前」，且引用单数 `.opencode/skill/`、`tests/`、`README.md`，现行布局下必然失败。

### 4.4 Windows 与部署形态

- `tool/show_markdown.ts:15` 硬编码 `startsWith("/")`，Windows 的 `C:\...` 必被判 `INVALID_PATH`；即便改写成 `/…`，`:38-51` 的 `path.resolve()` 也只落到当前盘根且无工作区边界校验，两种写法都取不到工作区内的表格。
- `python3`、`~`、反斜杠续行、`cd &&`、`$(pwd)`、heredoc、`<占位符>` 与 `.opencode/skills/…` 示例均不可移植。

### 4.5 本次配置复核新增

## 5. 统一路径约定与命令模板

按部署形态，唯一可行规范是：脚本路径 = 全局配置目录绝对路径；工作空间侧每个参数 = 工作空间绝对路径；由派发单注入工作空间根，禁用 `file/...`、`<会话目录>`、`~`。脚本侧 `check.py` 拼子命令前把所有路径 `os.path.abspath()` 并对非绝对路径 fail-fast，其余按 cwd 解析的脚本（`scan_outline.py`、`convert_office.py`、`export_tables.py`、`new_session_dir.py`、`screen_intent_words.py` 等）同样要求绝对路径；`new_session_dir.py` 输出绝对路径作为全链路锚点。`edit` / `bash` allow-list 同步改成绝对路径 glob。

```bash
python <全局配置目录绝对路径>/skills/test-point-spec/scripts/check.py --phase tc \
  --input-dir <工作空间绝对路径>/file/project-docs \
  --baseline  <工作空间绝对路径>/file/session-XXXXXX/scope/requirements-baseline.json \
  --tp-file   <工作空间绝对路径>/file/session-XXXXXX/output/tp/test-point.md \
  --tc-file   <工作空间绝对路径>/file/session-XXXXXX/output/tc/test-case.md \
  --report    <工作空间绝对路径>/file/session-XXXXXX/output/reports/check-tc.json
```

模板为 Linux 示意；Windows 下需按 4.4 的约定改写为单行绝对路径命令。
