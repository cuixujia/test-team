# `.opencode` 语义冲突检查报告

## 1. 检查范围与结论

检查对象为修复后的现行配置：3 份 agent、8 份 `SKILL.md`、13 个脚本、`tool/show_markdown.ts`、项目根 `opencode.jsonc`；以 `修复方案.md` 的修复意图作为判定口径的参照。

本报告只收录**硬语义冲突**：同一行为被两处以上以互斥方式规定，模型只能二选一；以及文档指定为「唯一权威」的对象自身给出两种答案。纯实现缺陷、单纯路径落空、Windows 适配、措辞差异不计入，仅在必要时作为伴生项列出。

结论：共发现 **12 条硬冲突**（P0 六条、P1 六条），另有 5 条会放大冲突的口径杂质。P0 集中在「阶段 3 机验」「确认关口前终轮」「qa-report 采信」三处，均会让模型在两条都被明文要求的路径之间反复摇摆，或触发补派死循环。P0 之外，脚本与文档在 `--only`、`--freeze-baseline`、引文分件命名、自检命令形态上仍有四类口径分裂。

## 2. P0 冲突：会直接改变流程走向

### 2.1 C1 阶段 3 机验脚本口径互斥

- 口径 A：`test-manager.md:89,91` 规定阶段 3 是「含基线阶段**最小机验**」，QA 收稿对账同轮只执行**一项**定向 `verify_requirement_baseline.py`，并称其为「基线摘录保真的**唯一裁决**」；同处明令 `verify_quotes.py` 喂基线 JSON 会退出码 2、**禁止用它替代基线机验**。`test-qa-expert.md:62,85` 的阶段 3 条目与职责段落同样只指向基线定向。
- 口径 B：`prd-quality-check/SKILL.md:61,63` 规定「每条原文摘录由 `verify_quotes.py` 对原文件逐字机验」「**全量由质检专家自行运行**」，并要求在报告机器关小节回填防伪四字段；该 skill 是 `test-qa-expert.md:26` 指定的阶段 3 强制加载项。
- 互斥点：阶段 3 尚无 TP/TC 清单，现场含摘录的工件只有 `requirements-baseline.json`（对象 JSON）；`verify_quotes.py:179-187` 对对象 JSON 直接 `ValueError`、退出码 2。B 的命令在此阶段必然失败，而 A 要求「只跑一项」并禁止该用法。
- 模型表现：按 B 执行后把退出码 2 记为「机器关 FAIL」→ 经理依 `test-manager.md:92` 判定基线对账未落盘并补派；或两个脚本都跑，违反「最小机验」且多出无法归档的工件；或跳过 B，使阶段 3 缺失被强制要求的机验与四字段。
- 统一方向：阶段 3 唯一机验脚本定为 `verify_requirement_baseline.py`，删除 `prd-quality-check/SKILL.md:61,63` 的全量 `verify_quotes.py` 要求，改由基线证据逐字裁决承接。

### 2.2 C2 「确认关口前必须全量」与 `--phase full` 唯一一次

- 口径 A：`test-manager.md:125` 无例外地写「增量机验由 QA 在复检轮执行，**确认关口前最后一次必须全量**」；`test-manager.md:123` 明确签字关口有 TP、TC **两处**，即关口①（阶段 7）与关口②（阶段 12）都在该句覆盖范围内。
- 口径 B：`test-manager.md:111,120` 规定 `check.py --phase full` **全程只在阶段 12 跑一次**；`test-manager.md:95`、`test-qa-expert.md:58`、`test-point-spec/SKILL.md:142` 规定关口①前终轮是 `--phase tp --freeze-baseline`。此外 `test-point-spec/SKILL.md:143`、`test-case-spec/SKILL.md:129` 又把用户删改后的增量复检称作「终轮全量兜底」，`test-case-spec/SKILL.md:103` 把派生视图的条件写作「终轮全量机验 PASS 后」。
- 互斥点：「全量」「终轮」「兜底」三词被赋给两种互斥命令。若「全量」指 `--phase full`，关口①前也得跑，直接违反「全程唯一一次」，且 `check.py:200-203` 要求 `full` 必填 `--tc-file`，阶段 6/7 没有 TC 主件、必退出码 2；若指「完整跑当前 phase、不带 `--only`」，则与 A 的字面要求不一致，模型无法判定关口①的 `--phase tp` 算不算全量。
- 模型表现：在关口①误跑 `--phase full` → 退出码 2 或出现第二次 full；或为守「唯一一次」跳过关口①终轮 → 漏 `--freeze-baseline`，基线未冻结即进确认关口；或把 A 当作不适用，修复后仅做 `--only` 增量就放行。
- 统一方向：把 `test-manager.md:125` 的「全量」明确改为「不带 `--only` 的当前 phase 终轮」，`--phase full` 一词专用于阶段 12，并同步 `test-point-spec/SKILL.md:143`、`test-case-spec/SKILL.md:103,129` 的「全量兜底/终轮全量机验」措辞。

### 2.3 C3 防伪四字段无处落盘

- 口径 A：`test-qa-expert.md:48,49,68` 要求「报告**机器关小节**回填防伪四字段」「机器关与语义关**分小节落盘**」，并把阶段 6/11 的小节「机器关」定义为「一句结论＋防伪四字段」；`test-manager.md:95,121,128`、`prd-quality-check/SKILL.md:63` 同样以「机器关小节」为防伪字段和 FAIL 转述的取数来源；`tdd-quality-check/SKILL.md:84-85` 的阶段 8 模板确有该小节。
- 口径 B：`test-qa-expert.md:68` 同时指定「阶段 3/8 模板见 `prd-quality-check` / `tdd-quality-check`」「阶段 6/11 的节结构以本文件下方『报告格式（阶段 6/11）』为**唯一定义**」。但 `prd-quality-check/SKILL.md:80-107` 的阶段 3 模板只有「结论／问题清单／基线对账／附录×3」，`test-qa-expert.md:70-77` 的阶段 6/11 模板只有「结论／问题清单／让步点／维度覆盖让步台账／复检第N轮」——两处唯一模板都**没有「机器关」小节，也没有防伪四字段栏位**。
- 互斥点：模型按「唯一定义」写就必然漏掉被强制要求的四字段；按 A 写就必须在唯一模板之外自造小节，构成结构违规。
- 模型表现：把命令原文、退出码、工件路径、sha256 塞进「结论」或「附录」栏 → 经理按 `test-manager.md:121` 做 `shasum` 比对时取不到工件路径，记「机器关未采信」并回传补派；或索性不写四字段，使 `test-manager.md:95` 的「采纳」无据。
- 统一方向：在阶段 3 与阶段 6/11 的唯一模板中补入「机器关」小节及四字段固定栏位，阶段 3/8/6/11 用同一定义。

### 2.4 C4 定向机验要求工件，脚本不产出工件

- 口径 A：`test-qa-expert.md:48` 把 `verify_requirement_baseline.py` 定向纳入「机器关（自执行）」，要求「**工件落盘 `output/reports/`**」并回填「工件路径＋工件 sha256」；`test-manager.md:91,119,121` 要求阶段 3 经理「按防伪字段形式核对后采纳」，且「机验一律由 QA 执行并落盘工件与防伪四字段」。
- 口径 B：`verify_requirement_baseline.py:88-92` 的参数只有 `--input-dir/--clarifications/--manifest/--freeze`，无 `--report`；`:240-244` 只向 stdout 打印 PASS/FAIL，`open()` 全部为读模式，脚本不写任何工件。而 `prd-record-spec/SKILL.md:89` 明定「**机器关采信以工件为准，stdout 不作数**」。
- 互斥点：阶段 3、阶段 4（CL 回写确认，`test-manager.md:93`）、阶段 9（基线增补，`test-manager.md:105`）的定向机验都要求「工件路径＋sha256」，但唯一被指定执行的脚本没有工件可登记；同时 stdout 又被明令不可采信。
- 模型表现：QA 把命令原文/退出码之外的两字段留空或填入基线 JSON 路径冒充工件 → 经理 `shasum` 比对对象错误；或按 `test-qa-expert.md:48` 的「派发单未附命令时声明机器关未采信」逻辑，把每次定向机验都判为不可采信，阶段 3 永远无法收口。
- 统一方向：要么给 `verify_requirement_baseline.py` 增加 `--report` 工件，要么在防伪四字段中为定向机验定义「工件＝基线 JSON＋其 sha256」的例外口径，并在三处 agent 中统一。

### 2.5 C5 报告节「不得回改」与「回填原小节」

- 口径 A：`test-qa-expert.md:68`、`prd-quality-check/SKILL.md:78,109`、`tdd-quality-check/SKILL.md:75,106` 一致规定「每节落盘终稿后**不得回改增删**；同阶段增量发现**新开小节**，不覆盖旧节」；`test-qa-expert.md:68` 枚举的节只有 §阶段3／§阶段6／§阶段8／§阶段11 四个。
- 口径 B：`test-manager.md:89,92` 规定基线未落盘时「汇合后单独补派一次基线对账」，结论写入原节内的「**§阶段3 资料体检 → 基线对账**」小节，且派发前必须核对该小节已存在；`tdd-quality-check/SKILL.md:85` 规定阶段 9 基线增补机验「**回填即在此小节**」（§阶段8 的机器关）；阶段 12 的 `--phase full`（`test-manager.md:111`、`test-qa-expert.md:61`）在节清单中没有对应落点。
- 互斥点：时间上后发生的补派、增补机验、终轮兜底都必须落盘，A 禁止回改终稿、要求另起新节；B 要求写回原节的指定小节，且经理按原节路径做字面核对。
- 模型表现：QA 按 A 新开「§阶段3 资料体检 · 复检第2轮」→ 经理按 `test-manager.md:92` 找不到「→ 基线对账」小节 → 判定挂起未补派并再次派发，形成死循环；或按 B 回改终稿节 → 报告指纹漂移，违反写作纪律；阶段 9/12 的机验则干脆无处回填四字段。
- 统一方向：为补派、阶段 9、阶段 12 各定义独立的新节名，并把 `test-manager.md:92` 的核对条件改为「原节或对应新节存在」。

### 2.6 C6 用户删改的落点互斥

- 口径 A：`test-manager.md:96` 规定「用户删改意见**按编号映射回主件修订并重导 table**」；`test-point-spec/SKILL.md:124,130`、`test-case-spec/SKILL.md:103,115` 规定「权威数据始终是主件」「确认关口与一切用户可见一律用 table」「**主件变更即视图失效**，机验 PASS 后重跑 `export_tables.py` 刷新」。
- 口径 B：`test-point-spec/SKILL.md:143` 规定「阶段 7 验收：**用户删改的行即刻生效、不回炉复检**（经理记录差异到状态档案）」，`test-case-spec/SKILL.md:129` 阶段 12 同句；只写 `state/status.md`（`test-manager.md:155`），不改主件、不重跑机验。
- 互斥点：A 要求改动主件并重导视图（指纹变化，牵动机验与派生），B 要求只记差异、不回炉复检，而「权威数据始终是主件」又禁止只改 table 不改主件。三者只能择一。
- 模型表现：只改 table → 后续 `check.py` 以主件为准，用户删改被静默回滚，且视图不再是只读投影；按 A 改主件并顺手重跑机验 → 违反 B 的「不回炉复检」；只在 `status.md` 记一行 → 用户确认的决策没有落到任何交付物。
- 统一方向：明确「用户删改＝改主件＋重导 table＋受影响行增量复检」，或明确「仅接受/拒绝整份清单、不做行级删改」，二选一后同步两份 `-spec` 与 `test-manager.md:96`。

## 3. P1 冲突：导致命令、工件或权限判断错误

### 3.1 C7 `--only` 能否跨 phase

- 口径 A：`test-manager.md:120`、`test-qa-expert.md:64`、`prd-record-spec/SKILL.md:90` 及 `check.py:181` 参数帮助一致写「`--only` **只接受当前 phase 内的步骤名**，拼错直接退出码 2」；`test-manager.md:120` 还指定「步骤集合以 `check.py` **头注释为准**」。
- 口径 B：被指定为准的 `check.py:14` 头注释写「`--only requirements-baseline` **可单独跑基线**」；`:232-238` 的 `extra={"requirements-baseline"}` 分支在 `--phase tp` / `--phase tc` 下放行该跨 phase 步骤并追加进 `selected`，而 `PHASE_STEPS["tp"]`/`["tc"]`（`:62-63`）并不含它。
- 互斥点：唯一权威（头注释）与三份文档对同一命令的合法性给出相反答案，脚本实际执行 B。
- 模型表现：不敢发 `--phase tp --only requirements-baseline`，放弃定向基线复验；或发出后预期退出码 2 却拿到 0，误判机验管线异常。
- 统一方向：保留跨 phase 例外就同步改写三份文档的「只接受当前 phase」，否则删除 `check.py:14` 与 `:232-238` 的例外分支。

### 3.2 C8 `--phase full` 能否带 `--freeze-baseline`

- 口径 A：`test-manager.md:96,111,120`「只在阶段 7 传入一次」「阶段 12 不传」、`test-qa-expert.md:61`「不传」、`check.py:15` 头注释「**仅在阶段 7**」、`:183` 参数帮助同句。
- 口径 B：`check.py:207` 的错误文案写「`--freeze-baseline` 仅阶段 7…**或 `--phase full` 可用**」，`:206` 的校验只禁止 `--phase tc`，`:240-241,356-357` 实现允许在 full 下把基线步骤与 `--freeze` 一起追加。
- 互斥点：同一脚本的头注释、参数帮助与参数校验/实现给出两种合法性，文档又规定阶段 12 不传。
- 模型表现：在阶段 12 的 `--phase full` 上带该开关 → 破坏「仅阶段 7 一次」，并对阶段 9 增补后的基线再跑一次 `--freeze` 校验；或按头注释认定 full 也禁止，与脚本报错文案冲突时反复改命令。
- 统一方向：以「仅阶段 7、`--phase tp`」为唯一口径，修正 `check.py:206-207` 的校验与文案。

### 3.3 C9 引文分件文件名

- 口径 A：`test-manager.md:95`「引文分件 `.quotes-tp.json`」、`test-designer.md:108`、`test-case-spec/SKILL.md:128`「`.quotes-tc.json` 等引文分件」、`check.py:18` 头注释「报告会读取 `.quotes-*.json`」。
- 口径 B：`check.py:272-273` 的 `quote_report_path()` 生成 `<report_stem>.quotes-<kind>.json`，`:326-329,341-344` 据此调用与回读，实际产物是 `check-tp.quotes-tp.json`、`check-tc.quotes-tc.json`。
- 互斥点：同一工件在文档与实现中是两个不同路径；`test-qa-expert.md:15-17` 的 `*.quotes-*.json` 授权能匹配实际产物，权限本身不冲突，冲突只在命名。
- 模型表现：防伪四字段的「工件路径」写成 `.quotes-tp.json` → 经理 `shasum` 找不到文件 → 记「机器关未采信」；按文档名复核引文 → 找不到分件，误判 `QUOTE_REPORT_MISSING`（`check.py:281`）。
- 统一方向：文档统一改用 `<report_stem>.quotes-<tp|tc>.json`，或让 `check.py` 输出点开头的固定分件名。

### 3.4 C10 自检命令缺 `python3` 前缀

- 口径 A：`test-designer.md:49` 要求「交稿前**必跑**只读自检」且「**任一 FAIL 不得交稿**」；`:55` 又规定「任一单项操作（写入/命令）**被拒，仅跳过该项**并记录原因，其余项照常执行」。
- 口径 B：`test-designer.md:50-53` 的四条自检命令均写 `<SKILLS_ROOT>/.../verify_*.py <参数>`，**不带 `python3`**；而同文件 `:80,97` 的命令模板、其余全部文档都写 `python3 <SKILLS_ROOT>/...`，且 `:22-26` 的 bash allow-list 每条都以 `python3 ` 为前缀。
- 互斥点：按 `:50-53` 原样拼出的命令不匹配任何 allow 规则（`:21` 的 `"*": deny` 兜底生效），必然被权限拒绝；此时 `:55` 允许跳过该项继续交稿，与 `:49` 的必跑/不得交稿直接对撞。
- 模型表现：四条自检全被拒 → 按 `:55` 汇总「被拒」清单后照常交稿，「必跑只读自检」被静默绕过，回到修复前的「零次校验脚本」状态。
- 统一方向：`:50-53` 补齐 `python3 ` 前缀；并规定「自检命令被权限拒绝」不属于 `:55` 的可跳过项，必须回传经理补授权。

### 3.5 C11 QA 机验命令的唯一来源

- 口径 A：`test-qa-expert.md:48`「机验由**你按派发单命令**自行运行」，且「派发单未附命令时声明『机器关未采信』并回传所需命令清单」；`test-manager.md:143` 的派发单【校验脚本】栏提供「可复制的绝对路径单命令」，但允许「**无则写无**」。
- 口径 B：`test-designer.md:54,77,94,112` 反复要求生成者交稿把 QA 机验命令附入「**待补跑命令清单**」；`test-manager.md:143` 又写「生成者另附只读预检命令」，`test-manager.md:130` 写「派发只给…校验命令」。
- 互斥点：同一条 QA 机验命令由派发单和生成者交稿清单两处定义，QA 只认前者；当派发单按模板写「无」时，即便生成者附了清单，QA 也必须判「机器关未采信」。
- 模型表现：经理认为「可由交稿清单补充」而在派发单写「无」→ QA 依 `:48` 拒绝执行并回传补派；或 QA 改按交稿清单执行 → 与「防伪四字段命令原文＝派发单实际命令」的口径不一致，报告不可重放。
- 统一方向：确定派发单为 QA 机验命令唯一来源，删除【校验脚本】「无则写无」，把生成者交稿清单限定为只读预检命令。

### 3.6 C12 自检记录写入主件与模板冲突

- 口径 A：`test-designer.md:49` 要求把自检「命令原文与退出码写入**主件『自检记录』**」。
- 口径 B：`test-point-spec/SKILL.md:84-98` 与 `test-case-spec/SKILL.md:65-79` 的清单模板只定义「主表＋覆盖表」两节，并明写「主件**不含状态字段**」「主件动状态字样＝动指纹＝**全链机验作废**」；`test-qa-expert.md:68` 把 `qa-report.md` 定为全流程唯一报告，`test-manager.md:155` 把状态与流水账归 `state/status.md`。
- 互斥点：模板未定义「自检记录」节，而该节必然含 PASS/FAIL 类状态字样；且 `check.py:324-325,339-340` 对主件全文扫描引用语法，新增章节中的 `文件:L行号「摘录」` 会被 `quote-tp`/`quote-tc` 当作引用一并机验。
- 模型表现：写进主件 → 触发「动指纹＝全链机验作废」或引文误抽；不写 → 违反「交稿前必跑自检」的记录要求，`test-manager.md:119` 的预检核对无据。
- 统一方向：自检记录改落 `state/status.md` 或独立自检文件；若必须留主件，需在两份 `-spec` 模板中明确定义该节并排除机验扫描。
