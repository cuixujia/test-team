# 开发设计文档质检规范

## 质检目的与深度

阶段 8 的目的：确认已验收测试点及其依据可继续使用，且生成 TC 十字段所需的适用设计资料可用。

- 检查深度 = **支撑 TC 生成**，不要求实现级精度。
- 本阶段无机械校验脚本兜底：可客观判定的事实（文件是否存在、是否可读、编号与需求证据可追溯）必须用工具核实，其余语义维度由你判断，**不凭印象下结论**。
- 材料未覆盖的：说明对 TC 生成的影响并登记缺口，**不得静默丢弃，不得替材料补造约束**。
- 开发设计文档为**硬前置**——未指定则流程中止（见下文「必需资料硬门槛」）。

## 输入资料范围

| 资料 | 要求 | 质检规则 |
|---|---|---|
| 阶段 7 已验收测试点 | 必需 | 确认状态为已验收、编号与需求证据（文件:行号+原话）可追溯，且覆盖当前目标功能 |
| 前端设计 | **适用时必需** | 功能含操作界面 → 必须有可读材料，检查页面入口、交互、校验、提示与适用的兼容性要求；纯接口/纯算法等无界面功能 → 登记「前端设计不适用」并继续 |
| 后端设计 | **必需** | 必须有可读材料；检查接口、状态、权限、异常、事务及适用的并发/幂等等约束 |
| 数据库设计 | 可选 | 有则检查字段、类型、长度、枚举、默认值和约束；无则登记「未提供」并继续 |
| 存量测试用例 | 可选 | 有则登记供阶段 10 参考；不得复制历史编号，不得取代已验收 TP；无则登记「未提供」并继续 |

### 必需资料硬门槛

前端、后端设计中经适用性判定为必需的项是**硬门槛**：

- 任一缺失、不可读，或存在影响用例步骤、测试数据、预期结果的未解决问题 → 结论为「**暂不可进入阶段 10**」，测试经理须请用户澄清或补充。
- 经理判定功能无界面时登记「前端设计不适用」继续；判定存疑（如 PRD 是否含界面描述不清）时请用户确认，登记结论后继续。
- 质检复核适用性判定：**PRD 明示界面要求却被判不适用时列为问题**。
- **不得将缺失的必需设计当作可选资料**，也不得自动豁免受影响 TP。用户明确要求带风险推进时，走 Blocker 二次确认规则并登记风险。

### 可选资料处理

- 缺失或为空 → 登记「未提供」并继续，不补造材料中不存在的约束。
- **存在但不可读** → 不得静默跳过，须列明影响并请用户处理或明确同意跳过。

## 五维检查

| 维度 | 必查：影响 TC 生成的内容 |
|---|---|
| 完整性 | TC 十字段所需细节：操作入口、字段约束、枚举、错误码、状态定义、异常路径能否从材料获得 |
| 一致性 | 设计材料与 PRD 已确认约束（需求基线+直引证据）的匹配；前端与后端设计文档之间接口契约一致 |
| 无二义性 | 歧义是否会改变 TC 的操作步骤、测试数据或预期结果 |
| 可测试性 | 预期结果可观察、可判定；测试数据可构造 |
| 可追溯性 | 每条设计约束能定位到具体文档与位置 |

## 材料专项检查项

| 材料类型 | 检查项 |
|---|---|
| 前端设计文档 | 页面元素与操作入口、交互事件、提示文案、前端校验规则、兼容性说明 |
| 后端设计文档 | 接口契约、状态机定义、并发与锁、事务边界、批处理时序、错误码表、幂等约定 |
| 数据库设计（可选） | 字段类型/长度/枚举值、默认值、主外键与级联约束 |
| 存量测试用例（可选） | 场景与步骤参考；不得复制编号或将历史用例当作本次验收依据 |
| 接口文档 | 请求/响应字段约束、错误码表、幂等约定、签名加密规则 |
| 流程图/时序图 | 分支完整性、异常路径、超时处理（不可解析时触发降级声明） |

> **超长文档必须分页读完**，禁止只读首屏下结论。

## 问题分级

沿用两级分级，判定基准为 **TC 可生成性**：

- **Blocker**：受影响 TP 的 TC 无法生成或预期无法判定
- **Major**：可暂定 TC，但缺口可能改变 TC 的步骤、测试数据或预期结果

## 报告载体与模板（五合一）

本阶段结论写入 `output/reports/qa-report.md` 的「**§阶段8 用例资料体检**」节（qa-report 是全流程唯一 QA 报告，分节追加，节落盘后不得回改）。节内结构：

```markdown
## 阶段8 用例资料体检：目标功能 <目标功能>

### 结论
Blocker: N 项 / Major: N 项
是否可进入阶段 10：是 / 否（原因）

### 材料清单
| 材料类型 | 路径/文件名 | 必需/可选 | 提供情况 | 可读性与相关性 | 检查范围/结论 |
|---|---|---|---|---|---|

### 问题清单
| 问题编号 | 维度 | 材料来源 | 问题描述 | 级别 | 该出依据（知识②/③或补充件条目；缺件致该维度应出而未出时填） | 恢复条件（补件后复核动作） | 改进建议 | 对测试的影响 |
|---|---|---|---|---|---|---|---|---|

（"该出依据/恢复条件"两列为**维度覆盖让步台账**的源头采集位（qa-report 阶段 6/11 台账小节的收口素材）：凡因材料缺件导致知识②/③某维度应出而未出对应 TP/TC 的，必须填写这两列；一般问题留空。复制规则见 `agents/test-qa-expert.md` 报告格式。）

> **处置状态单一权威**：缺件/让步/澄清处置由测试经理登记于 `state/clarifications.md`（CL 表），本报告**不设处置记录表、不回填处置**（双记账必漂移）。复检报告只记录本轮变化。

### 附录：候选判定留痕
| 候选 | 处置（登记/不登记） | 一行理由 |
|---|---|---|

> 挑战位：若您发现本报告未列出的疑似缺失或矛盾，请直接提出，我将按判据核实后补充登记或说明不登记理由。
```

命名规则：同阶段复检增量**新开小节**（如「§阶段8 用例资料体检 · 复检第2轮」），不覆盖旧节；一律只写 qa-report.md，不另建单件报告。

## 措辞要求

「问题描述」「对测试的影响」两列按「现状（哪里写了什么）→ 差异/缺失 → 影响」直白句式，一句话说清。

## 处置协议

1. 用户补充材料后：复查受影响问题，处置结论交经理登记 CL（处置状态以 CL 表为唯一权威，本报告不回填）；受影响产物按材料变更协议处理。
2. Blocker 未清零：声明风险 → 用户二次确认 → 状态档案登记降级决策。
3. 前端、后端或数据库设计后续变更时，只复查受影响 TP/TC。
