# 溯源锚点底册规范

## 底册的作用

锚点底册是**全流程唯一溯源底册**。测试点的依据、覆盖对照表的核对单元、质检的引用校验，全部以底册为准。

底册是整个流程的**信任根**：底册有错，下游全部"合规的假证据"。因此底册必须**先建后用、逐条质检**。

## 锚点编号规则

按以下优先级取用，**不新建编号体系**：

1. **PRD 已有编号体系**（如 `REQ-001`、`3.2.1`、`FUNC-04`）→ 直接使用 PRD 原文编号作为锚点编号。
2. **PRD 无编号** → 按 `M<模块号>-S<章节号>-P<段落号>` 建立（如 `M1-S2-P3` = 模块1 / 第2章节 / 第3段落；无段落细分时 `P0` 表示整节）。
3. 锚点编号一经登记**不得变更、不得复用**。补录走受控变更流程。

## 原文摘录规则

摘录是底册的价值所在，规则从严：

| 规则 | 说明 |
|---|---|
| 长度 | **≤40 字**（含底册行） |
| 连续 | 取 PRD **连续原句**，**禁止跨段拼接** |
| 逐字 | 与 PRD 原文**逐字一致**，禁止改写、调整语序、增删标点 |
| 定位 | 能唯一定位到 PRD 中的位置（章节标题 + 摘录） |
| 支撑 | 摘录所支撑的信息，必须就是该锚点要验证的业务信息 |

**摘录必须程序化提取，禁止手抄**——手抄是摘录漂移的根因。用 `scripts/extract_excerpt.py` 从 PRD 原文按锚点定位提取，脚本同时输出字符数供自检。

## 底册落库格式

```markdown
# <目标功能> 溯源锚点底册

## 锚点清单
| 锚点ID | 来源PRD文件 | 章节定位 | 原文摘录 | 关联功能编号 |
|---|---|---|---|---|
| <锚点ID> | <PRD 文件名> | <章节/位置> | <≤40字连续原文> | <BF01> |

## 引用链登记
| 锚点ID | 来源PRD文件 | 章节定位 | 原文摘录 | 关联功能编号 |
|---|---|---|---|---|
```

> **列序为校验契约**，`scripts/verify_anchors.py` 按此表名与列序解析，禁止调整。

### 各列说明

- **锚点ID**：按上文编号规则。
- **来源PRD文件**：该锚点所在的 PRD 文件名（任务可能涉及多份 PRD）。
- **章节定位**：锚点在 PRD 中的位置（章节号或标题），供人工回溯。
- **原文摘录**：≤40 字连续原文。
- **关联功能编号**：该锚点支撑的业务功能编号（`BF01` 等），取自任务功能清单。

### 引用链登记

目标功能的业务规则/界面/完成标准中，每处**对其他功能的引用及操作入口归属**（如「编辑/复制/删除分别在 FUNC-04/05/06 定义」），逐项登记入引用链表：锚点取被引功能编号，摘录取引用处原句。仅作检索入口，不展开被引功能全文。

## 建册流程

1. 从任务功能清单读取本次任务覆盖的功能编号与功能名称。
2. 通读 PRD，围绕**已选定的功能**逐条建锚点——**不得为未选定的功能预建锚点**。
3. 每条摘录用脚本程序化提取，自检字符数 ≤40。
4. 登记引用链。
5. **自检**：运行 `scripts/verify_anchors.py`，检查摘录是否真实存在于 PRD 原文、是否超长、锚点是否重复、关联功能编号是否在任务功能清单内。不通过则修复后重跑。
6. 底册建立后**冻结**，交由质检专家在阶段 3 独立复核。

## 冻结与补录

- 底册建立后冻结，全流程以此为准。
- **唯一例外**：阶段 3 资料质检的**漏锚扫描**发现缺口时，须经**用户确认**后由经理受控补录，并在状态档案「变更登记」记 `底册补录 v<N>`。
- 补录后必须重跑自检。

## 降级

PRD 为 PDF / 图片等不可文本化材料时：

- 在底册标题下写 `> 摘录机验：跳过（<原因>）`；
- 摘录机验随之降级，`scripts/verify_anchors.py` 输出 WARN 并跳过该子项；
- **降级前必须先尽力自行消化**：内嵌图片/流程图应解包提取并读图，结论以「AI 解读待确认」标注登入底册；仅当确实无法解读且影响判定时才降级并交用户确认——**禁止把能自行消除的不确定性推给用户**。
