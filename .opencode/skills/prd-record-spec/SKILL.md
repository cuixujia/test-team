# 溯源锚点底册规范

## 底册的作用

锚点底册是**全流程唯一溯源底册**。测试点的依据、覆盖对照表的核对单元、质检的引用校验，全部以底册为准。

底册是整个流程的**信任根**：底册有错，下游全部"合规的假证据"。因此底册必须**先建后用、逐条质检**。

## 锚点编号规则

按以下优先级取用，**不新建编号体系**：

1. **PRD 已有编号体系**（如 `REQ-001`、`3.2.1`、`FUNC-04`）→ 直接使用 PRD 原文编号作为锚点编号。
2. **PRD 无编号** → 按 `M<模块号>-S<章节号>-P<段落号>` 建立（如 `M1-S2-P3` = 模块1 / 第2章节 / 第3段落；无段落细分时 `P0` 表示整节）。
3. 锚点编号一经登记**不得变更、不得复用**。补录走受控变更流程。

## 原文摘录规则

摘录是底册的价值所在，规则从严：

| 规则 | 说明 |
|---|---|
| 长度 | **≤40 字**（含底册行） |
| 连续 | 取 PRD **连续原句**，**禁止跨段拼接** |
| 逐字 | 与 PRD 原文**逐字一致**，禁止改写、调整语序、增删标点 |
| 定位 | 能唯一定位到 PRD 中的位置（章节标题 + 摘录） |
| 支撑 | 摘录所支撑的信息，必须就是该锚点要验证的业务信息 |

**摘录必须程序化提取，禁止手抄**——手抄是摘录漂移的根因。用 `scripts/extract_excerpt.py` 从 PRD 原文按锚点定位提取，脚本同时输出字符数供自检。

## 底册落库格式

```markdown
# <目标功能> 溯源锚点底册

## 锚点清单
| 锚点ID | 来源PRD文件 | 章节定位 | 原文摘录 | 关联功能编号 |
|---|---|---|---|---|
| <锚点ID> | <PRD 文件名> | <章节/位置> | <≤40字连续原文> | <BF01> |

## 段落账
| 段落定位 | 处置 | 说明 |
|---|---|---|
| <锚点ID 或段落/范围标识> | 已建锚 / 范围外 / 待确认 | <一句话说明> |

## 引用链登记
| 锚点ID | 来源PRD文件 | 章节定位 | 原文摘录 | 关联功能编号 |
|---|---|---|---|---|
```

> **列序为校验契约**，`scripts/verify_anchors.py` 按此表名与列序解析，禁止调整。

### 各列说明

- **锚点ID**：按上文编号规则。
- **来源PRD文件**：该锚点所在的 PRD 文件名（任务可能涉及多份 PRD）。**摘录逐字命中按此文件精确比对**——这个字段必须写准确的文件名，否则脚本只能退回全目录比对。
- **章节定位**：锚点在 PRD 中的位置（章节号或标题），供人工回溯。
- **原文摘录**：≤40 字连续原文。
- **关联功能编号**：该锚点支撑的业务功能编号（`BF01` 等），取自任务功能清单。

### 段落账

建册时把**所选范围内 PRD 的每个段落**逐段登记处置，三态取一：

- **已建锚**：该段已登记锚点（枢纽段落，说明其支撑内容）。
- **范围外**：该段与本任务功能无关（写明一句原因，如「NFR 性能约束，用户已裁决不纳入」）。
- **待确认**：疑似该建锚但拿不准，交阶段 3 复核。

任何段落不得缺登记。段落账是阶段 3 漏锚抽查的基准——质检据此抽验，而不必重读 PRD 全文。

### 引用链登记

目标功能的业务规则/界面/完成标准中，每处**对其他功能的引用及操作入口归属**（如「编辑/复制/删除分别在 FUNC-04/05/06 定义」），逐项登记入引用链表：锚点取被引功能编号，摘录取引用处原句。仅作检索入口，不展开被引功能全文。

## 提取策略（按 PRD 格式分档，避免无效重跑）

摘录提取是**机械活**：同一份机械劳动被多个执行者重复 N 遍，就是长任务最大的耗时源。以下策略决定「谁提取、怎么提取」。

### docx / doc 类（无 markdown 标题）——最高频坑

脚本按 markdown 标题或行首编号定位。docx 解析后**通常没有任何 `#` 标题行**，因此：

| 定位串 | 是否可用 | 说明 |
|---|---|---|
| 章节号 `1` `2.1` `3.1` `4.3` `5` `7.2` | ✅ 可用 | 行首带编号的标题行 |
| 功能名 / 模块名（`删除风险`） | ❌ 失败 | 不是标题行，定位不到 |
| `BR-DEL-01` / `FUNC-06` / `GOAL-01` | ❌ 失败 | 行首不是数字，定位不到 |
| `M1-S6-P3` | ❌ 失效 | 该形式依赖 markdown 标题，docx 下取不到 |

**正确做法**：用**编号章节**作定位串，一次 `--candidates N` 取回该章节全部候选句，再从中点名采用：

```bash
# 一次取回整章候选（长句用 --max-chars 300 取回整句，便于挑选 ≤40 字片段）
python3 scripts/extract_excerpt.py --prd-dir <PRD目录> --locate "6" --max-chars 300 --candidates 900
```

**不要为每条摘录单开一次调用**——一次整章枚举 + 一次点名，取代 N 次「换定位串试提取」。

### 长句（>40 字）的取法

底册摘录上限 40 字，但关键业务句常常更长。两步取法：

1. `--max-chars 300` 取回**整句**（含编号 token）；
2. 登记时从整句中取 **≤40 字的连续片段**（优先包含 `BR-xxx-xx` 这类编号 token，便于人工回溯），在提取记录里标注「全句 → 子串」的截取区间。

片段必须**逐字来自脚本输出**，不得改写、不得跨句拼接。

### 标点必须逐字一致

**摘录的字符以脚本的解析结果为准，不是以你读到的渲染效果为准。** 同一条 PRD 内容，`textutil` 渲染与 `word/document.xml` 解析可能给出**不同的引号字符**（直角 `"` vs 弯引号 `“ ”`）；`verify_anchors.py` 比对的是**脚本解析出的文本**，且只做**空白规范化**、**不规范化标点**——引号差一个字符即判「未逐字命中」。

**因此：摘录直接从脚本输出那一行复制粘贴，不要自己敲，也不要"顺手规范化"标点。** 若不确定某句的实际字符，以脚本输出为准重新取一次。

> 实测提醒：本次任务中 `textutil -convert txt -stdout` 显示的是弯引号 `“ ”`，而 `extract_excerpt.py` / `verify_anchors.py` 的 docx 解析结果是直角引号 `"`。**以脚本输出为准**。

### 分工：收割归经理，收口归专家

摘录提取不需要设计判断。建册阶段的分工固定为：

| 环节 | 执行者 | 产出 |
|---|---|---|
| 摘录收割（跑脚本、按章枚举、点名候选） | **经理** | 摘录清单：锚点ID / 来源文件 / 章节定位 / 逐字摘录 / 定位串 / 候选序号 / 字符数 |
| 建册判断（哪段建锚、哪段范围外、哪段待确认） | **经理**（多切片时并行起草专家协助判断） | 段落账处置结论 |
| 写盘 + 自检（按模板落盘 + 跑校验 + 交指纹） | **设计专家** | `scope/anchors.md` + 校验输出 + [SHA256] |

**一条硬规则**：**缺摘录时由经理补跑脚本，不新开一轮设计会话**——补链是机械活，重开一轮会把整个阶段拖长数倍。

## 建册流程

1. 从任务功能清单读取本次任务覆盖的功能编号与功能名称。
2. 通读 PRD，围绕**已选定的功能**逐条建锚点——**不得为未选定的功能预建锚点**。
3. 每条摘录用脚本程序化提取，自检字符数 ≤40；**多条锚点用 `extract_excerpt.py --locate-file <定位串清单>` 批量提取**（一次调用取回全部，劣势条件下也不要一条一次反复调用）；`--candidates N` 可让脚本一次给出 top-N 候选句，由你点名最贴切的一句，避免反复换定位串试提取。**docx 类 PRD 按上文「提取策略」用编号章节整章枚举**。
4. 登记段落账（逐段三态处置）。
5. 登记引用链。
6. **自检**：运行 `scripts/verify_anchors.py`，检查摘录是否真实存在于 PRD 原文（按来源文件比对）、是否超长、锚点是否重复、关联功能编号是否在任务功能清单内。不通过则修复后重跑。
7. 底册建立后**冻结**，交由质检专家在阶段 3 独立复核。

## 冻结与补录

- 底册建立后冻结，全流程以此为准。
- **唯一例外**：阶段 3 资料质检的**漏锚扫描**发现缺口时，按**两步受控补录**执行：
  1. 经**用户确认**后，经理在状态档案「变更登记」记 `底册补录 v<N>`，并以派发单派发 `test-designer` 执行补录（写底册的权限在设计专家，单一写入者不变；经理只登记版本、不直接动底册）；
  2. 设计专家按派发单补录锚点、登记段落账，**重跑自检**通过后交回（随附完整输出与 [SHA256]）。
- 补录期间该功能切片的流程暂停，其余功能可继续。

## 降级

PRD 为 PDF / 图片等不可文本化材料时：

- 在底册标题下写 `> 摘录机验：跳过（<原因>）`；
- 摘录机验随之降级，`scripts/verify_anchors.py` 输出 WARN 并跳过该子项；
- **降级前必须先尽力自行消化**：内嵌图片/流程图应解包提取并读图，结论以「AI 解读待确认」标注登入底册；仅当确实无法解读且影响判定时才降级并交用户确认——**禁止把能自行消除的不确定性推给用户**。
