# 测试点（TP）规范

## 定义

**测试点（TP）是一项供产品确认、可判定通过或不通过的业务验证目标。** 它说明验证哪项业务能力，以及结果应符合什么方向。

**测试点分类（知识④§1.2）**：按验证目标分**功能级**（单功能点内，挂叶子功能点下）与**场景级**（跨功能点链路，挂载规则见知识④§1.2）；主表「类型」枚举中的「流程」即对应场景级 TP。

测试数据、操作步骤、具体预期文案归测试用例（TC）。TP 不按字段、输入值、角色或控件逐项拆分——这些维度由关联的 TC 分别覆盖。

**TP 数量不作为目标。** 按业务目标与切分规则决定数量：不为减少条目而漏掉不同规则，也不为增加覆盖而把同一目标拆碎。

## 一条 TP 必须同时满足三条（缺一不许出）

### 一 · 说得出出处

每条 TP 必须挂至少一个**证据**（格式与规则见 `prd-record-spec`），证据分两类：

- **直引证据**：`文件:L行号「≤40字原话」`——指出资料哪句话支撑它，原文逐字复制。验证的事必须就是这句话说的事，不许拿一句话当幌子验它没说的内容。
- **澄清证据**：资料没写但用户澄清补充的规则，挂到澄清记录编号（`CL-001`）。必须注明推导来源，且不得与主资料明文矛盾。

两条都占不住的，按无依据处理，**禁止产出**。

### 二 · 切得不多不少（按业务能力切，不按字段切）

**判定标准以知识库为准**：功能点拆分与测试点粒度执行知识④《测试点生成指南》§二（拆分规则）、§四（颗粒度标准）、§六步骤 5（全集覆盖自检 `(a)~(f)`）。

切分与合并的团队判别细则（PRD 锚定三条件、合并规则、"该拆该合"两句话、三违规反例）见 `test-knowledge/references/补充-TP切分与命名判别.md` §一——质检（阶段 6）按同一文件执行，质检与生成用同一判据。

**描述不清的交接**：PRD 没说明并列条件是否存在不同规则 → 先按同一目标合并成一条，并把该模糊点记入资料质检报告的问题清单要求澄清，**不得自行补造规则**（判据与合并动作在补充件 §一，交接登记在此）。

### 三 · 判得了对错

写完必须能回答：「真执行了，**看什么能分出过/不过？**」（如「看交易是否被拒」）——不用写出具体文案和数字，但要能说出看哪个结果。答不上来就先别出：要么先要求 PRD 澄清，要么承认现在验不了。

**通过判定口径**：TP 所含 PRD 要求**全部满足**才算通过，任一未满足即该 TP 不通过；各 TC 结果分别记录，便于定位失败维度。

## 命名

**以知识④§三为准**：

- 功能级 TP：`验证` + `操作对象` + `基础功能`
- 场景级 TP：`验证` + `跨模块流程描述`（可用"-"串联关键节点）
- 禁止行为清单见知识④§3.3（不机械全覆盖、不凑数、不重复、不臆造）

团队补充口径（对象抄 PRD 原词、短语级 ≤30 字、判错口袋清单）见 `test-knowledge/references/补充-TP切分与命名判别.md` §二。

## 边界：TP 不是什么

**一 · 不是功能描述**：功能点 =「系统能做什么」，不出现「验证」字样；TP =「验证什么」。每个末层功能点必须有 TP，空功能点违规。

**二 · 不是测试用例**：TP 不带步骤、数据、具体预期文案。TP:TC = 1:N（N≥1）——一条 TP 至少派生一条 TC；一条 TC 可关联一个主要 TP 和相关 TP，但必须保持一个明确的通过/失败目的。

**三 · 覆盖不全不行**：识别时按知识②的大类→维度→小类扫描（功能：正常/异常/边界 + 界面/兼容/安全/性能），领域强化检查单见 `test-knowledge/references/补充-领域检查单.md`；非功能型 TP 仅在 PRD 提及或高风险时生成。

## 一致性与基线

- TP 排列顺序 = 其依据证据在主资料中的出现顺序（文本事实，锁定排序）。
- 阶段 7 验收通过的清单即**基线**：此后只有受控变更（失效/新增/修改），编号只增不复用，禁止无差别重生成。

## 字段规范

| 字段 | 要求 |
|---|---|
| 编号 | `TP-NNN`，三位序号，本次任务内连续，只增不改不复用；**不含业务功能编号** |
| 验证意图 | 按命名格式；能独立判断对错 |
| 类型 | 功能 / 异常 / 边界 / 流程 / 非功能（单选） |
| 分析方法 | 来源方法名（等价类/边界值/判定表/因果图/场景法/状态迁移/正交实验/错误推测/探索性测试；方法定义与选型见知识①） |
| 依据 | 每项以证据 token 开头；至少一个证据，多项用保留分隔符 ` ⟂ ` 分隔。直引证据 = `文件:L行号「≤40字原话」`（须与原文逐字一致）；澄清证据 = `CL-xxx` + 结论要点 + 推导来源（编号须在澄清记录中）；禁止无依据 TP |

## 清单模板

```markdown
# <目标功能> 测试点清单

（主件**不含状态字段**：更新状态字样须动主件=动指纹=全链机验作废，零消费还招假信息——「已确认仍写草稿」实测发生过。确认/冻结状态唯一权威 = `state/status.md`。2026-11-06 瘦身）

| 编号 | 验证意图 | 类型 | 分析方法 | 依据（文件:行号+原话） |
|---|---|---|---|---|

## 需求→测试点覆盖表
| 需求ID | 覆盖的 TP 编号 | 未覆盖原因 |
|---|---|---|
（需求基线内每条需求必须出现；范围外或不测试必须给出已确认的原因）
```

**排序规则（2026-11-06 新增，便于实际执行为唯一准）**：TP 编号顺序按执行动线编排——同一操作对象/页面/主流程步骤的 TP **连续相邻**；禁止同一对象间隔多行后反复回流（如 TP-001 表单A、TP-002 表单B、TP-003 回表单A 即为编排缺陷；跨对象集合型/全链路型 TP 除外，须显式声明）。排序缺陷是 TP 级问题，交设计专家重排（改主件），不阻塞语义判定本身。

> **列序为校验契约**，`scripts/verify_test_points.py` 按此解析，禁止调整。
>
> **覆盖对照表（证据→测试点）不再是交付物**（2026-11-05 收敛）：该表可从主表自动推导，由 `check.py` 的 `derive-coverage-table` 步骤生成数据视图（`check-<phase>.derived-coverage.md`，与报告工件同目录、同指纹绑定）。专家不再手工维护——此前它贡献了证据漏登 3 行、原因列误填 53 行、转义 FAIL 一整类纯格式返工。若手工提供该表，校验器仍按既有契约对其进行一致性校验（防止与主表矛盾）。

## 派生数据视图（test-point-table.md，只读投影）

权威数据始终是本清单主件。视图由**经理**在**语义质检修复闭环、终轮全量机验 PASS 后**（用户确认关口前）用脚本派生——语义质检与修复只看主件，提前出表必随主件修复作废重导（2026-11-06 收敛，出表时机后移）；**确认关口以 table 为载体、用户可见均用 table**；语义质检仍看主件，table 不单独承载语义：

- **视图文件只包含一张表**（无标题、无引语）：列 = 编号 / 验证意图 / 类型 / 依据（指针化）/ 所属系统 / 业务活动 / 业务功能；
- 依据列**指针化**：直引证据取 `文件:行号`、澄清证据取 `CL-xxx`，以「、」连接；不保留原话——保真与语义以主件机验裁决；
- 所属系统 / 业务活动取自 `state/scope-list.md`「归属登记」表按功能名称查得；查不到按标签规范留空并 WARN；
- 业务功能 = `需求→TP 覆盖表` 反查 TP→REQ → 基线 `feature_id` → `selected_scope` 中对应**功能名称原文**（编号不进视图；name 缺失时降级并 WARN，视图自检 exit 1）；
- **映射时效**：主件变更即视图失效——机验 PASS 后由经理重跑 `export_tables.py`，数据自动跟随主件刷新，不存在人工同步步骤。

```bash
python3 .opencode/skills/test-point-spec/scripts/export_tables.py --phase tp \
  --tp-file <test-point.md> --baseline <requirements-baseline.json> \
  --scope-list <scope-list.md> --output <test-point-table.md>
```

行数与编号集合同主表自洽（脚本内置断言，不一致 exit 1）。主件变更即视图失效，须重新生成。

## 交付约束

- 最终交付的测试点清单中**不得出现业务功能编号**——归属用业务功能名称原文表达。
- 交付前运行 `scripts/check.py --phase tp --report <output/reports/check-tp.json>`，生成绑定资料、需求基线和测试点指纹的机器报告（内含引文逐字、基线、TP 结构、追溯四关与报告新鲜度自检）；FAIL 必须修复后重跑。质检专家核验报告工件与指纹，不重复跑相同机械检查。
- 资料只收纯文本（md/markdown/txt/csv）；摘录一律逐字复制，保真由 `prd-record-spec/scripts/verify_quotes.py` 机验裁决；定位可用 grep/read 或 `extract_excerpt.py`。

## 变更规则

- 阶段 7 验收：**用户删改的行即刻生效、不回炉复检**（经理记录差异到状态档案）；若需设计专家按删改影响继续修订，修订后只对**受影响行**走质检的**增量复检**（复检范围见质检阶段 6，终轮全量兜底），编号只增不改不复用。
- 设计材料变更 → 受影响 TP 标记失效，失效 TP 禁止派生 TC。
- 用户澄清 PRD「没说清」的问题后 → 按切分规则重新合并/拆分受影响 TP，并对受影响行跑增量复检。
- TP 基线错误经用户确认调整 → 回阶段 5 受控变更，编号只增不改不复用，删除 TP 仅标记废弃。
