# 测试点（TP）规范

## 定义

**测试点（TP）是一项供产品确认、可判定通过或不通过的业务验证目标。** 它说明验证哪项业务能力，以及结果应符合什么方向。

测试数据、操作步骤、具体预期文案归测试用例（TC）。TP 不按字段、输入值、角色或控件逐项拆分——这些维度由关联的 TC 分别覆盖。

**TP 数量不作为目标。** 按业务目标与切分规则决定数量：不为减少条目而漏掉不同规则，也不为增加覆盖而把同一目标拆碎。

## 一条 TP 必须同时满足三条（缺一不许出）

### 一 · 说得出出处

每条 TP 必须挂一个**锚点**（锚点来自溯源锚点底册），锚点分两类：

- **PRD 原文锚点**：指出 PRD 哪句话支撑它，抄下 ≤40 字原文——验证的事必须就是这句话说的事，不许拿一句话当幌子验它没说的内容。
- **澄清锚点**：PRD 没写但用户澄清补充的规则，挂到澄清记录编号（`CL-001`）。必须注明推导来源，且不得与 PRD 明文矛盾。

两条都占不住的，按无依据处理，**禁止产出**。

### 二 · 切得不多不少（按业务能力切，不按字段切）

- **合并规则**：PRD 将多个条件**并列列在同一业务能力下**，且没有为它们规定不同的流程、规则、权限或结果 → 合成一条。即使某项可能单独出错，也不因此拆分；该项由 TC 单独覆盖，TC 结果分别记录以便定位问题。
- **拆分规则**（仅以下情况拆分）：
  1. 条件属于**不同业务能力或不同业务目标**
  2. PRD **明文规定**了不同的流程、规则、权限或结果
  3. **主项与副项**承担不同作用，且 PRD 对两者规定了不同的操作或验收要求
- 字段、数据、角色、控件不同，或其中一项可单独失败——**本身都不是拆分理由**。
- **描述不清**：PRD 没说明并列条件是否存在不同规则 → 先按同一目标合并成一条，并把该模糊点记入资料质检报告的问题清单要求澄清，**不得自行补造规则**。

**质检两句话**：

- **该拆**：两种结果出自 PRD 明文规定的不同流程/规则/权限/结果，或分属不同业务目标 → 拆成两条。
- **该合**：同一业务能力下的并列条件、或同一规则下的不同数据/对象/角色 → 合成一条（由 TC 覆盖各维度）。

**三违规**：

1. **太大**：把 PRD 写明不同规则的多条业务塞进一条（如「验证转账功能正确」）
2. **太小**：同一套处理的不同数据拆成多条——若 PRD 对 0 和负数写的是同一套「拒绝并提示」，具体数据是用例的事
3. **耦合**：验证明细维度的存在性/生效性与其所属能力验证重复 → 只保留能力级验证，细则由 TC 覆盖

### 三 · 判得了对错

写完必须能回答：「真执行了，**看什么能分出过/不过？**」（如「看交易是否被拒」）——不用写出具体文案和数字，但要能说出看哪个结果。答不上来就先别出：要么先要求 PRD 澄清，要么承认现在验不了。

**通过判定口径**：TP 所含 PRD 要求**全部满足**才算通过，任一未满足即该 TP 不通过；各 TC 结果分别记录，便于定位失败维度。

## 命名

**「验证」+ 对象 + 结果方向**，短语级（≤30 字）：

- 对象**直接抄 PRD 的叫法**，不自创同义词——名称是未来用例库检索键
- 结果方向照实际写（受理、拒绝、提示重输、挂起……这些是例子不是封闭清单）
- 禁止：具体预期表现（提示文案/错误码/账务变化/具体数值）、操作步骤、系统能力描述

| 示例 | 判定 |
|---|---|
| 验证超单笔限额的转账被拒绝 | ✅ 一条逻辑、一个结果方向、PRD 原词 |
| 验证高级搜索按支持条件筛选风险 | ✅ 同一搜索能力下的八项并列条件合并为一条；各条件由 TC 覆盖 |
| 验证详情信息完整展示 | ✅ 同一详情完整性要求下的多个展示字段合并；字段清单由 TC 核对 |
| 验证转账功能正确 | ❌ 几条不同业务规则塞一条，没法判 |
| 验证输入 0 元和负数均被拒绝 | ❌ PRD 写的是同一套处理——具体数据是用例的事 |
| 验证系统能转账 | ❌ 功能描述，不是验证 |

## 边界：TP 不是什么

**一 · 不是功能描述**：功能点 =「系统能做什么」，不出现「验证」字样；TP =「验证什么」。每个末层功能点必须有 TP，空功能点违规。

**二 · 不是测试用例**：TP 不带步骤、数据、具体预期文案。TP:TC = 1:N（N≥1）——一条 TP 至少派生一条 TC；一条 TC 只挂一条 TP。

**三 · 覆盖不全不行**：识别时全维度扫描——功能（正常/异常/边界）+ 界面/兼容/安全/性能 + 领域检查单（见 `test-analysis-methods`）；非功能型 TP 仅在 PRD 提及或高风险时生成。

## 一致性与基线

- TP 排列顺序 = 其依据锚点在 PRD 中的出现顺序（文本事实，锁定排序）。
- 阶段 7 验收通过的清单即**基线**：此后只有受控变更（失效/新增/修改），编号只增不复用，禁止无差别重生成。

## 字段规范

| 字段 | 要求 |
|---|---|
| 编号 | `TP-NNN`，三位序号，本次任务内连续，只增不改不复用；**不含业务功能编号** |
| 验证意图 | 按命名格式；能独立判断对错 |
| 类型 | 功能 / 异常 / 边界 / 流程 / 非功能（单选） |
| 分析方法 | 来源方法名（等价类/边界值/判定表/场景法/状态迁移/正交实验/错误推测） |
| 依据 | 以锚点 token 开头：PRD 锚点 = 锚点ID + ≤40 字原文摘录（**须与底册登记逐字一致**，脚本机械校验）；澄清锚点 = `CL-xxx` + 结论要点 + 推导来源（编号须在澄清记录中，脚本机械校验）；每条 TP 只挂一个锚点；禁止无依据 TP |

## 清单模板

```markdown
# <目标功能> 测试点清单（状态：草稿 / 质检后 / 已验收）

| 编号 | 验证意图 | 类型 | 分析方法 | 依据（锚点+原文摘录） |
|---|---|---|---|---|

## 覆盖对照表（锚点→测试点）
| 锚点ID | 覆盖的 TP 编号 | 未覆盖原因 |
|---|---|---|
（底册中每个锚点都必须出现在本表；未覆盖项填写原因、禁止留空）
```

> **列序为校验契约**，`scripts/verify_test_points.py` 按此解析，禁止调整。

## 交付约束

- 最终交付的测试点清单中**不得出现业务功能编号**——归属用业务功能名称原文表达。
- 交付前运行 `scripts/verify_test_points.py`（参数：清单、`--ledger` 底册、`--scope-list` 任务功能清单、`--clarifications` 澄清记录），退出码非 0 时必须修复后重跑；把完整输出（含尾部 [SHA256] 行）交回经理。
- PRD 支持 md/markdown/txt/doc/docx；摘录一律用 `prd-record-spec/scripts/extract_excerpt.py` 提取。

## 变更规则

- 阶段 7 验收调整 → 修订对应行并重跑阶段 6 质检（经修复循环后重新验收）。
- 设计材料变更 → 受影响 TP 标记失效，失效 TP 禁止派生 TC。
- 用户澄清 PRD「没说清」的问题后 → 按切分规则重新合并/拆分受影响 TP，并重跑阶段 6 质检。
- TP 基线错误经用户确认调整 → 回阶段 5 受控变更，编号只增不改不复用，删除 TP 仅标记废弃。
