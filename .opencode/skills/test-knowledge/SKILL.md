# 测试知识库（唯一权威知识源）
> **路径基准**：`<SKILLS_ROOT>` 默认 `~/.config/opencode/skills`（Linux 下由 shell 展开，换机器自动跟随 HOME），由派发单【路径基准】注入实际绝对路径；`<WORKSPACE_ROOT>` 为工作空间根目录绝对路径。本文中的脚本路径取 `<SKILLS_ROOT>/<skill>/scripts/...`，跨 skill 资源取 `<SKILLS_ROOT>/<skill>/references/...`，输入与产物取 `<WORKSPACE_ROOT>/file/session-XXXXXX/...`；命令发出前须替换为实际绝对路径，禁止相对路径与残留占位符。


本 skill 不定义任何规则本身，只登记知识清单、阅读路径和维护规则。**所有测试语义判定的最终依据在这里，其它 skill 只能引用、不得复述。**

## 一、知识清单

路径锚点：附属知识件位于 `<SKILLS_ROOT>/test-knowledge/references/`（`<SKILLS_ROOT>` 默认 `~/.config/opencode/skills`）。前四份为**原文只读件**，一字不改：

| 文件 | 解决什么问题 | 关键章节 |
|---|---|---|
| `references/1 通用测试方法论.md` | 用什么方法测 | §5 方法详解、§7 方法选型决策指南 |
| `references/2 测试维度定义.md` | 从哪些维度测 | §二 维度明细、§三 维度选型指南（银行场景→维度组合） |
| `references/3 通用测试规则.md` | 每个维度具体测什么 | §一 功能测试（1~6 维度逐项关注点）、§二 非功能测试、附录对应关系 |
| `references/4 测试点生成指南.md` | 测试点怎么拆、怎么命名、怎么从需求推导 | §二 功能点拆分、§三 命名规范、§四 颗粒度、§五 模板库、§六 生成工作流程 |
| `references/补充-TP切分与命名判别.md` | 团队对知识④的判别细则与反例补充 | 见文件内目录 |
| `references/补充-领域检查单.md` | 银行/Web/接口领域强化检查单（知识③的领域加强版） | 见文件内目录 |
| `references/补充-TC列判据.md` | TC 三列（标题/测试数据/步骤/预期结果）语义判据 + TP 命名两条词法（验证词去重、过粗校正） | 见文件内目录 |

补充件可增改；前四份原文不可变——需要修订知识原文时，由用户决定整体替换文件。

## 二、阶段阅读路径

| 阶段 | 必读 | 用途 |
|---|---|---|
| 阶段 5 生成测试点 | 原文④§二/§三/§四/§六 → 补充《TP切分与命名判别》（含裁决十） | 拆功能点、定测试点、命名、颗粒度与全集自检 |
| 阶段 5 维度展开 | **原文②全文**（§二 维度明细 33 小类 / §三 维度选型指南 / §四 使用建议）+ 原文③附录对应关系 | 按业务功能逐小类判定资料是否提及，命中项逐项出 TP（裁决十） |
| 阶段 5 域质材料 | 原文①§7 | 分析方法选型；方法详解按需查 §5 |
| 阶段 6 质检测试点 | 原文④（粒度与命名判据） + 补充件（含裁决十） | 独立语义检查的判据来源；逐小类复核覆盖 |
| 阶段 10 生成测试用例 | 原文③对应维度关注点 + 补充《领域检查单》+ 补充《TC列判据》 | 在已确认 TP 下展开场景、数据与三列判据；**小类不在此阶段落到 TC** |
| 阶段 3/6/8/11 质检 | 按上述路径取对应判据 | 质检发现须落到知识条目上 |

## 三、维护规则

1. 原文四份为生效知识，不改动；调优只动**补充件**，或经用户决定整体替换原文。知识原文以 `<SKILLS_ROOT>/test-knowledge/references/` 为唯一权威。
2. 原文内保留的「工作流程/步骤」表述一律按**判定方法**理解；工序交接与产物形态（清单/报告/命令）以 skill 层契约为准（`prd-record-spec`、`test-point-spec`、派发单）。
3. 其它 skill 与本文档口径不一致时，**以本文档为准**：改 skill 的复述为引用，不改知识。

## 四、业务规则供给

- 业务特有测试规则不做系统级知识，由用户以输入资料方式提供：若用户提供了业务规则，则参考用户的规则；未提供时不叠加、缺项走澄清，不得臆造。
